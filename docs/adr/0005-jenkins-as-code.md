# ADR 0005 — The Jenkins controller is configured only from code

Status: accepted

## Context

A Jenkins controller that has been configured through its web UI keeps its
configuration in `$JENKINS_HOME`. That state is invisible in review, hard to
recreate, and the usual recovery plan is a backup of a directory nobody has
tested restoring. "Ask the person who set it up" is not a deployment procedure.

## Decision

The controller image installs its plugins from `jenkins/plugins.txt` at build
time, and everything else comes from `jenkins/casc.yaml` via the Configuration
as Code plugin: the admin account, authorization, the build agent, credentials,
and the release job itself (through Job DSL). The setup wizard is disabled.

Two consequences of that choice needed solving rather than clicking around:

* **The agent's connection secret** is generated by Jenkins when it creates the
  node, so it cannot be written into the compose file. The agent's entrypoint
  authenticates to the controller and reads its own secret from the node's
  `.jnlp` descriptor before connecting.
* **Optional credentials.** Artifactory settings come from environment
  variables that are empty by default. The pipeline checks whether a credential
  actually holds a value before binding it, so a local run reports publishing as
  skipped instead of failing.

The controller keeps zero executors and builds only on the labelled agent, so a
runaway build cannot take the controller with it.

## Consequences

* `make up` produces an identical controller every time; deleting the volume
  costs nothing.
* Changes to the Jenkins setup arrive as reviewable diffs.
* The job definition lives next to the code it builds.
* Configuration as Code does not cover every plugin setting in existence; the
  ones it does not cover would need a Groovy init script, which is a cost this
  project has not had to pay yet.
